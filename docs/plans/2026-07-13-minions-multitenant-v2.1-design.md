# Minions 企业多租户系统 2.1 设计方案

**版本：** 2.1 已实现
**日期：** 2026-07-13
**基线：** 2.0 生产安全修订版
**目标：** 在不安装 PostgreSQL 的开发环境中完成可运行、可迁移、可验证的企业多租户系统；生产和租户模式只允许 PostgreSQL，禁止静默退回 SQLite。

---

## 1. 2.1 的完成定义

2.1 不是“令牌中增加 tenant_id”，而是下面六个条件同时成立：

1. 每次请求都先解析成服务端签发、不可由请求正文伪造的 `TenantPrincipal`。
2. Tenant、User、Membership、Role、Agent、Invite、Session、Audit、Quota 都进入统一控制平面。
3. Web、Agent 子路由、SSE、渠道、Cron、ACP 和内部任务使用同一套主体与授权规则。
4. Agent 列表、读取、修改、运行和工作区访问全部经过租户归属校验；跨租户一律返回不存在或拒绝访问。
5. SAGE 直接消费同一个可信主体，经验、案例、候选心得与审核记录天然带租户边界。
6. SQLite 开发库能够完整运行与测试；切到 `tenant/production` 时必须配置 PostgreSQL，否则启动失败。

## 2. 核心架构

采用“模块化单体 + 控制平面 + 租户工作区”的结构：

```text
浏览器 / 渠道 / Cron / ACP / 内部任务
                │
                ▼
        Principal Attestation
     身份校验、会话校验、主体绑定
                │
                ▼
        Tenant Policy Gateway
      权限、租户状态、Agent 归属、配额
                │
       ┌────────┴────────┐
       ▼                 ▼
 Control Plane       Agent Runtime
租户/用户/成员/审计    工作区/工具/渠道/任务
       │                 │
       └────────┬────────┘
                ▼
             SAGE
       案例、经验、心得、巩固
```

控制平面是唯一的身份和归属事实源。现有 `config.json` 继续承担运行配置，但不再决定“谁能看到哪个 Agent”。

## 3. 全新命名

多租户模块统一命名为 `minions.tenancy`，不复用旧记忆系统或旧多租户实验命名。

| 概念 | 2.1 名称 | 作用 |
|---|---|---|
| 可信调用者 | `TenantPrincipal` | 不可变主体、权限与租户上下文 |
| 控制平面 | `TenancyService` | 领域规则和事务边界 |
| 策略入口 | `TenantPolicyGateway` | fail-closed 授权 |
| 开发存储 | `SQLiteTenancyStore` | 单文件、事务化、自动迁移 |
| 生产存储 | `PostgresTenancyStore` | 连接池、RLS、运行时最小权限 |
| Agent 归属 | `AgentGrant` | Agent 与租户、拥有者、访问级别 |
| 成员关系 | `TenantMembership` | 用户在租户中的角色和状态 |
| 邀请 | `TenantInvite` | 有期限、一次性、可撤销 |
| 审计 | `TenantAuditEvent` | 追加写、可追溯 |

SAGE 保持独立名称，但身份来源只允许 `TenantPrincipal.to_sage_identity()`。

## 4. 数据模型

所有主键使用 UUID。所有租户资源表显式包含 `tenant_id`，唯一约束也包含 `tenant_id`。

### 4.1 核心实体

- `tenants`：名称、slug、状态、版本、创建时间。
- `users`：全局登录名、展示名、密码摘要、状态、版本。
- `tenant_memberships`：租户、用户、角色、状态；一个用户可属于多个租户。
- `auth_sessions`：令牌摘要、用户、租户、到期、撤销时间、最近使用时间。
- `tenant_invites`：目标租户、角色、令牌摘要、到期、使用状态。
- `agent_grants`：全局运行时 Agent ID、租户、拥有者、访问级别、状态。
- `tenant_quotas`：Agent 数、成员数、并发任务和存储上限。
- `tenant_usage`：配额计数及乐观锁版本。
- `tenant_audit_events`：操作者、动作、对象、结果、请求关联号、脱敏元数据。

### 4.2 角色

- `owner`：租户生命周期、成员、Agent、SAGE、审计和配额全权管理。
- `admin`：成员、Agent、SAGE 和审计管理，不能移除 owner 或删除租户。
- `operator`：使用与维护 Agent、渠道、Cron、SAGE 审核。
- `member`：使用被授权的 Agent、查看自身业务数据。
- `viewer`：只读。

角色映射到细粒度权限；业务代码只检查权限，不直接判断角色名。

## 5. 身份与会话

### 5.1 登录

登录输入为用户名、密码和可选租户 slug。服务端验证后只签发当前租户会话。令牌包含：

- `session_id`
- `tenant_id`
- `user_id`
- `issued_at`
- `expires_at`
- 随机 nonce

令牌使用服务端密钥签名；数据库仅保存令牌摘要。登出、成员停用、租户停用和密钥轮换都能立即失效。

### 5.2 开发模式

明确无认证的本地开发模式会自动建立一个 `local` 租户和 `local-admin`，但这个主体由服务端生成，不能从 Header 或请求正文传入。租户/生产模式严禁本地免认证绕过。

### 5.3 外部入口

- 渠道调用使用所属 Agent 的租户服务主体，再把渠道用户写入业务 actor 字段。
- Cron 使用创建者或指定服务主体，成员被停用后任务自动拒绝。
- ACP 使用短期、指定 Agent、指定权限的服务会话。
- 内部维护任务使用不可登录的 service principal。

## 6. 授权与隔离

授权顺序固定为：

1. 主体存在且会话有效。
2. 租户处于 active 状态。
3. 成员关系 active。
4. 具备动作权限。
5. 资源 `tenant_id` 与主体一致。
6. Agent 处于 active 且访问级别允许。
7. 未超过配额。

任何一步无法证明允许，就拒绝。跨租户资源读取优先返回 404，降低资源枚举风险。

## 7. Agent 与工作区

- 新 Agent 默认路径：`WORKING_DIR/tenants/{tenant_id}/workspaces/{agent_id}`。
- Agent 的运行时 ID 保持全局唯一，避免当前 WorkspaceRegistry 缓存键碰撞。
- `agent_grants` 是归属事实源；`config.json` 只保存运行时引用。
- Agent 创建采用“预留配额 → 创建工作区 → 保存配置 → 建立归属 → 写审计”的补偿事务。
- 删除先归档、撤销运行权限、停止实例，再进入延迟清理；API 不直接跨目录物理删除。

## 8. SAGE 自我成长闭环

2.1 把经验成长纳入租户治理：

1. 普通业务完成后生成服务器可验证的 outcome。
2. 自动抽取“做法、结果、适用条件、风险、证据”。
3. 形成租户内案例和候选心得。
4. 低风险心得按租户策略自动生效；中高风险进入审核。
5. 夜间巩固进行聚类、冲突检测、合并、降权和归档。
6. 下次相似业务召回时附带来源、置信度、版本和使用回执。
7. 使用效果反哺评分，错误经验可回滚并保留审计链。

SAGE 不接收请求方自报的 tenant_id、verified outcome 或决策摘要；这些值必须来自绑定主体和服务器执行记录。

## 9. 管理界面

新增“企业空间”页面，面向非技术用户，包含：

- 空间概览：当前租户、成员数、Agent 数、配额与风险提醒。
- 成员与角色：邀请、改角色、停用、撤销邀请。
- Agent 归属：拥有者、状态、授权范围。
- 审计记录：时间、操作者、动作、对象、结果。
- 经验治理：待审核案例/心得、批准、拒绝、回滚。

登录页支持选择可用企业空间；侧边栏显示当前空间和角色，不暴露数据库术语。

企业空间的生命周期由控制面完成：首个所有者可创建后续企业空间，同一全局账户可
拥有多个租户成员关系；创建、页面内切换和登录选择都会签发只绑定单一租户的新会话，
并撤销被替换的旧会话。邀请令牌只展示一次，已有账户接受第二个空间邀请时必须同时
验证原账户密码。

## 10. 存储策略

### SQLite 开发

- `WAL`、外键开启、busy timeout。
- 所有多步写入使用显式事务。
- 同一进程写串行化。
- 用于开发、演示和自动化测试。

### PostgreSQL 生产

- 必须安装 `minions[postgres]` 并配置 DSN。
- 使用连接池、短事务、参数化查询。
- 每个请求在事务内设置可信 `tenant_id`，RLS 作为第二道防线。
- 复合索引以 `tenant_id` 为首列；外键列建索引。
- runtime 角色无建表、无绕过 RLS、无超级用户权限。

## 11. 迁移与回滚

1. 首次启动先备份控制文件并建立控制平面库。
2. 把现有单用户身份迁移为首个 owner，密码摘要保持原算法并在登录后升级。
3. 把现有 Agent 全部绑定到首租户，不移动工作区。
4. 校验数量、路径、归属和审计后写入迁移完成标记。
5. 新 Agent 才使用租户目录；旧路径在明确的离线迁移窗口再移动。
6. 迁移可重复执行；失败时不写完成标记、不启用 tenant/production 模式。

## 12. 验收门槛

- 两个租户同名业务数据互不可见。
- 修改 Header、路径、正文中的 tenant_id 都不能越权。
- viewer 不能执行写操作，operator 不能管理 owner。
- 停用成员后既有令牌立即失效。
- 停用租户后 Web、渠道、Cron、ACP 全部停止访问。
- SQLite 并发写没有丢失更新；迁移可重复执行。
- tenant/production + SQLite 必须启动失败。
- PostgreSQL schema 通过 RLS、索引、最小权限静态验证。
- 前端能完成登录、查看空间、成员、Agent、审计和经验审核。
- 所有者能创建第二个企业空间并在两个空间间切换；普通成员不能创建空间。
- 修改全局账户资料后，分布在全部企业空间的旧会话全部失效。

## 13. 2.1 之后不再遗留的关键债务

- 不再使用单用户 `auth.json` 作为在线身份事实源。
- 不再仅凭 `X-Agent-Id` 或 URL 就加载 Agent。
- 不再让本地免认证策略进入租户/生产模式。
- 不再让渠道、Cron 和 ACP 绕过统一主体。
- 不再让 SAGE 使用请求方自报的租户或“已验证结果”。
- 不再把 SQLite 当作可自动降级的生产数据库。
